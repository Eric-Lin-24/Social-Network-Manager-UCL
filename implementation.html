Implementation

How Community Curator is implemented across the Electron desktop app and the Python backend engines.

Windows Application

The Windows client is an Electron desktop application that combines project planning (timeline, people, calendar) with cloud-document browsing and outbound message scheduling. It provides a single UI to operate across Microsoft 365, Google Drive, and the backend APIs.

Application Structure

The app uses a clear process split: Electron main process for OS integration and OAuth callbacks, preload for secure bridging, and renderer modules for state, views, and API adapters.

Social-Network-Manager-UCL/ |- main.js # Electron main process, OAuth, IPC |- preload.js # contextBridge API exposed to renderer |- renderer.js # app bootstrap and auth flow |- simpleStore.js # local persisted key/value store |- src/renderer/ | |- appState.js # single shared client state object | |- azureVMAPI.js # messaging engine API wrapper | |- microsoftGraphAPI.js # OneDrive/Graph integration | |- googleDriveAPI.js # Google Drive integration | |- notifications.js # toasts + theme | `- views/ # timeline, people, scheduling, settings, ... `- styles.css

Key Features Implementation

1. Multi-provider Authentication and Token Persistence

The app supports both Microsoft and Google sign-in. Microsoft uses MSAL with a file-based persistent cache, while Google tokens are restored into the OAuth client at startup. This avoids repeated sign-in for returning users.

// main.js const msalConfig = { auth: { clientId: process.env.MICROSOFT_CLIENT_ID, authority: 'https://login.microsoftonline.com/organizations' }, cache: { cachePlugin: { beforeCacheAccess: async (ctx) => { const cacheLocation = path.join(app.getPath('userData'), 'msal-cache.json'); if (fs.existsSync(cacheLocation)) { ctx.tokenCache.deserialize(fs.readFileSync(cacheLocation, 'utf-8')); } }, afterCacheAccess: async (ctx) => { if (ctx.cacheHasChanged) { fs.writeFileSync(cacheLocation, ctx.tokenCache.serialize()); } } } } }; oauth2Client.setCredentials({ access_token: storedGoogleAccessToken, refresh_token: storedGoogleRefreshToken, expiry_date: storedGoogleTokenExpiry });

2. Unified Message Scheduling UI (Telegram + Email)

The Scheduling page consolidates queue management and draft management into one flow. Users compose once, then switch between Telegram queue, Email queue, and Drafts without leaving the screen.

Channel-aware queue rendering

The renderer stores channel queues in AppState and conditionally renders the correct queue tab with shared recipient formatting and status badges.

// src/renderer/views/scheduling.js function setSchedulingTab(tab) { AppState.schedulingActiveTab = tab; renderScheduling(); } const totalScheduled = messages.length + emails.length; // Tabs: Telegram Queue | Email Queue | Drafts // Content switches by AppState.schedulingActiveTab
Draft and queue design choices

The scheduling UX was implemented with these technical choices:

  • Single composer reused for both channels to reduce UI duplication.
  • Drafts persisted in local storage for fast recovery after restarts.
  • Shared recipient-resolution helper for both Telegram and Email queue cards.
  • Incremental card animations to improve visual scan of long queues.

3. Cloud File Synchronization and Source Switching

The Documents view supports OneDrive and Google Drive via one switchable state model. It validates provider authentication, refreshes cloud files, and preserves per-provider navigation context.

// src/renderer/helpers.js function switchDocumentSource(source) { if (source === 'googledrive' && !AppState.googleDriveConnected) { showNotification('Please connect to Google Drive first in Settings', 'warning'); navigateTo('settings'); return; } AppState.activeDocumentSource = source; renderDocuments(); const hasSourceDocs = AppState.documents.some(d => d.source === source); if (!hasSourceDocs) { source === 'onedrive' ? refreshOneDriveDocs() : refreshGoogleDriveDocs(); } }

UI Components

State Orchestration and Secure IPC Boundary

A more implementation-critical part of the desktop app is the security boundary between Electron processes. The renderer holds UI state in AppState, but privileged operations (OAuth and file access) are only reachable through preload-exposed IPC methods. This reduces attack surface compared with exposing full Node APIs to the page context.

// preload.js contextBridge.exposeInMainWorld('electronAPI', { login: () => ipcRenderer.invoke('msal-login'), getAccessToken: () => ipcRenderer.invoke('get-access-token'), googleLogin: () => ipcRenderer.invoke('google-login'), getGoogleDriveFiles: () => ipcRenderer.invoke('get-google-drive-files'), downloadGoogleDriveFile: (fileId, fileName, mimeType) => ipcRenderer.invoke('download-google-drive-file', { fileId, fileName, mimeType }) }); // renderer.js window.electronAPI.onAuthError((error) => { showNotification('Authentication failed: ' + error, 'error'); });

Performance Optimizations

  • Windows runtime stability: Electron user-data and cache directories are explicitly set to avoid permission/cache failures on Windows hosts.
  • GPU fallback: Hardware acceleration and GPU shader cache are disabled in Electron startup to reduce GPU-related crashes in student lab environments.
  • Demand-driven sync: Documents are only auto-synced when source data is missing, reducing unnecessary cloud API calls.
  • Stateful rendering: View updates are scoped by active tabs and views to avoid full-page reflows on every interaction.
  • Background polling cadence: backend schedulers run at a 5-second interval, balancing near-real-time delivery with low compute overhead.

Error Handling

Frontend API wrappers use defensive checks (URL configured, user authenticated, payload validation), parse server error payloads where possible, and surface actionable feedback to users through toasts.

Engine

The backend is implemented as two FastAPI services: App-Backend (identity + planning domain) and Telegram-Engine (message/email scheduling + delivery). The Electron client talks to both services directly.

Engine Architecture

App-Backend/ |- api.py # user, workspace, project, team, timeline endpoints |- auth.py # bcrypt hashing + verification |- database.py # SQLAlchemy engine/session + lightweight migrations |- models.py # users/workspaces/projects/team members/timeline models `- main.py # process bootstrap (port 8080) Telegram-Engine/ |- api.py # telegram/email scheduling + subscription endpoints |- scheduler.py # async background jobs for due deliveries |- telegram_messenger.py |- gmail_messenger.py |- database.py # SQLAlchemy engine/session |- models.py # scheduled messages, recipients, email models `- main.py # API + telegram bot process bootstrap (port 8000)

Controller endpoints are grouped by responsibility: planning data (workspaces/projects/tasks) in App-Backend, and communications scheduling in Telegram-Engine.

Service Layer

Business logic is split into authentication and scheduling services to keep route handlers focused on request parsing and response formatting.

Password Hashing and User Provisioning Service

# App-Backend/auth.py def get_password_hash(password: str) -> str: pwd_bytes = password.encode('utf-8') salt = bcrypt.gensalt() return bcrypt.hashpw(pwd_bytes, salt).decode('utf-8') def create_user(db: Session, user: UserCreate) -> User: db_user = User( username=user.username, hashed_password=get_password_hash(user.password), uuid=str(uuid.uuid4()) ) db.add(db_user) db.commit() db.refresh(db_user) return db_user

Delivery Scheduler Service

The scheduler continuously checks for due Telegram messages and due emails, dispatches each item through the relevant messenger module, and updates message state in the database.

# Telegram-Engine/scheduler.py async def check_and_send_due_messages(): while True: db = SessionLocal() due_messages = db.query(ScheduledMessage).filter( ScheduledMessage.scheduled_timestamp <= datetime.utcnow(), ScheduledMessage.is_sent == False ).all() for msg in due_messages: results = await send_message_to_users(msg.target_user_id, msg.message, msg.file_paths) msg.is_sent = True db.commit() await asyncio.sleep(5)

Data Access Layer

Both engines use SQLAlchemy with repository-style session dependencies via FastAPI Depends. SQLite is the default for local development, with environment variable override for PostgreSQL.

# App-Backend/database.py DATABASE_URL = os.getenv('DATABASE_URL', 'sqlite:///./accounts.db') engine = create_engine( DATABASE_URL, connect_args={'check_same_thread': False} if DATABASE_URL.startswith('sqlite') else {} ) SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine) def get_db(): db = SessionLocal() try: yield db finally: db.close()

Database Schema

The implementation uses separate schemas for planning data and messaging data. Core entities are shown below.

users (App-Backend)

  • id (PK, Integer)
  • username (unique)
  • hashed_password
  • uuid, created_at

timeline_tasks (App-Backend)

  • id (PK, String UUID)
  • project_id, assignee_id
  • start_date, end_date
  • hours_per_week, status, owner_uuid

scheduled_messages (Telegram-Engine)

  • id (PK, String UUID)
  • from_sender, target_user_id (JSON)
  • message, scheduled_timestamp
  • file_paths (JSON), is_sent, created_at

Background Jobs

Background processing is event-loop based. Two async jobs run concurrently: one for Telegram and one for Email. Both jobs poll due records every 5 seconds and mark completed records as sent.

# Telegram-Engine/scheduler.py def start_message_scheduler(app): @app.on_event('startup') async def start_schedulers(): asyncio.create_task(check_and_send_due_messages()) asyncio.create_task(check_and_send_due_emails())

Caching Strategy

  • MSAL Token Cache: Microsoft OAuth token cache is serialized to msal-cache.json in the Electron user-data directory and loaded on startup.
  • Google Token Cache: Google access and refresh tokens are persisted in SimpleStore and restored into oauth2Client credentials.
  • UI State Cache: Client state (sidebar collapse, theme, drafts) is stored locally to reduce repeated API calls and improve startup continuity.
  • In-memory Working Sets: AppState keeps active queue/documents/people data in memory for fast view transitions, refreshed on explicit sync actions.

Security Implementation

Security is implemented as layered controls across authentication, process isolation, secrets management, and input handling. The current architecture prioritizes practical protections for a multi-service student project while keeping a clear path for production hardening.

Password Storage

Passwords are never stored in plaintext. App-Backend uses bcrypt salt+hash generation during registration and bcrypt verification during sign-in, which protects against direct database disclosure of user credentials.

Renderer Isolation

Electron exposes a narrow, allowlisted API through preload contextBridge. The renderer cannot directly call arbitrary Node.js modules, so high-privilege operations stay in the main process.

Secrets in Environment

OAuth credentials, bot tokens, and SMTP settings are loaded from environment variables (.env) and never hard-coded in renderer views. This supports environment-specific deployment and safer key rotation.

Upload Segregation

Attachments are written to a dedicated uploads directory with generated UUID-based names. This avoids filename collisions and reduces path manipulation risks from user-provided filenames.

Authentication Guards in Client API Layer

Before scheduling/deleting messages, the renderer validates required auth context (Azure URL configured and active user ID present). This prevents unauthenticated accidental calls from the UI workflow.

Backend Schema Validation

FastAPI request models and typed form/query parameters enforce structure at the API boundary, reducing malformed payload handling and improving predictable error responses.

Current hardening opportunities: tighten CORS allowlists by environment, add token-based authorization to App-Backend endpoints (instead of trusting user_uuid alone), and add file type/size validation for uploads server-side.

The Python services use structured logging with clear lifecycle and processing logs. Scheduler logs include message IDs, recipients, send outcomes, and restart/shutdown events. This supports debugging and operational audits during local runs and VM deployments.
